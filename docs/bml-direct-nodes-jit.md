# BML to nodes directly, JIT instead of lowering

Where it stands (measured 2026-11-13, one-def edit to `observe/local-plan-run.bml`, `FKWU_CACHE_REPORT=1`, `observe/page-watch-run.bml`):

- A 59,464-byte door becomes 201,998 bytes of lowered Form text (`.lowfk`) and a 38,391,347-byte image (`.fkb`), 645 times its source, because the closure of 351 units is assembled whole.
- A cold build costs 0.37 s per MiB of image produced, about 3 MB/s, from 239 KiB (0.27 s) to 32 MiB (12.08 s); a warm read of the same image is 0.18 s. A trivial door importing the planner's 12 units alone costs 7.63 s. The synthetic 179 KB unit with one import lowers in 0.76 s, so the lowerer is not slow per byte of one unit; the cost follows the closure.
- The cold build is the Form lowerer run by `fk_cell_run_door` in the cold walker: BML text -> grammar templates (`bmf-grammar.fk` `template-emit`, strings) -> Form text -> C parse (about 17% of the beats) -> node rows -> a flat image written at 9 bytes a value (`fk_fkb_write_signed`).
- Strings are the seams between stages and also the cache keys, so one edit invalidates a whole closure while the unit of meaning is the recipe.

Where it goes: BML parses to nodes, each recipe is content-addressed by its own NodeID, the kernel JITs a recipe on first call and keeps the page under that id. An edit changes one NodeID, cold is the re-JIT of what changed, warm is reading pages by id (bandwidth).

Steps, each measured against the planner door's 12.94 s cold and 7.63 s trivial-door cold, each landed through the sibling-validation path:

1. A kernel native that appends one code node row (op and operands) so a Form producer can build nodes without the text hop; the grammar's templates then build nodes, and the Form text becomes a lens, not the pipe. Check: the door's digests equal the text route's.
2. The cache keyed on each recipe's content id, not the file text.
3. Lazy linking: a first call pulls the recipe's node and page; unit top-level lets run on first use, not at load.
4. A compact integer encoding for what is still written.

What step 1 had to carry (read from `runtime/fkwu-uni.c`): the code node row is appended by `fk_smknode(t0, c1, c2, c3)`, and only the C text parser called it. The same parser also resolves reserved heads (`defn do let if`, rewrite and op rows), binds names to slots, answers `[shadowed-call]`, checks arity and keeps the hidden-definition and diagnostic tables. A Form producer that builds nodes takes over those duties, and the kernel gives it the doors that the parser's tables hide.

Where step 1 stands (2026-11-13; witnessed by `observe/jit-node-witness-run.bml`, 10 of 10, and `form/form-stdlib/tests/source-node-emit-band.bml`, verdict 31):

- The door is `jit_node` (leaf-door mode 57), its words: `["node" t c1 c2 c3]` appends one row (a walker tag 1..255, all four fields stated; a short spec, a fifth element, a non-int field and a tag outside the walker's space are refused, never padded or read short); `["defn" name arity]` registers a function the way the parser's prescan does (the name's bytes in the source text as the image loader puts a symbol, its row in the name table, its arity); `["body" idx node]` binds its body once; `["lookup" name]` and `["arity" idx]` read the table; `["run" k]` walks a node in the caller's frame; `["why"]` names the cause of the last refusal (codes at `fk_jit_why`). A word longer than any it knows is an unknown word (why 1); it used to end the process. `kids` and `mint` grow their buffer until every leaf fits (they refused past 16 leaves). A tag-50 row is pinned as a tag-24 row is, in `fk_smknode`, so a built row and a parsed row cannot drift.
- The grammar's templates already intern recipe nodes (`bmf-grammar.fk` `gx-build`); `fbl-lower` rebuilds them as source-compiler recipes; the text hop is only the printer `fsc-source-emit-recipe`. So the first node-emitting piece is the printer's sibling, `form/form-stdlib/bml/source-node-emit.bml`: a recipe becomes rows with no text between. It carries int and string leaves, names bound by a parameter, calls to the ops of `flt-ops()` and to registered functions, and defn (slots, tag 111 over a body that needs more than slot 0, the body bound). It refuses by name what it does not carry yet: `do`, `let`, `if`, `match`, a float or bool leaf, a call through a bound name, an unbound name.
- It also carries `do` (tag 69), a `let` in a `do` (tag 109, the slot counter threaded through the whole defn as `fk_maxslot` is), `if` (tag 6), recursion, and the compare and logic ops, which are rewrite rows of `runtime/fkwu-optable.h` (the walker mirrors them as data; the band reads the header and fails when they drift). `form-stdlib/tests/source-node-emit-band.bml` reads verdict 511: nine claims, each built function answering as the same expression written in BML.
- Measured (2026-11-13, the 80-byte recipe `do (let a 1) (let b (add a x)) (if (eq b 0) 100 (add a b))`, 3000 emits in one process): the text printer `fsc-source-emit-recipe` costs 15 microseconds a recipe, the node walker 116 microseconds, 7.7 times the printer. The C parse that follows the printer is not in that figure and is microseconds for 80 bytes. So the text hop is not where the cold build spends its time, and swapping the printer for per-node `jit_node` calls does not make the cold build faster: each call builds a list and crosses the door. What would: step 2 (the cache keyed on the recipe's content id, so an unchanged recipe is never lowered at all), and a batch spelling of the door (one call carrying many rows, children by relative index) if emission is ever the cost. The cold build's time is in the Form lowerer and the 645-times image, as the profile said; the walker is the correct shape for the node route, not yet the fast one.
- What stays the producer's: children are node ids it was given (the door does not check a child is a live row); names, slots and arity are its own bookkeeping. A node-built function is registered in the process, not yet written into an image's function table, so step 2's cache keyed on the recipe's content id has to write it.
