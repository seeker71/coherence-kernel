# Form agent: the active contribution path

The resident Form agent is a long-lived `fkwu` process, not an HTTP service and
not a wrapper around llama-server or Ollama. Its working path is:

1. Birth executable capability nodes in the residence and announce their exact
   current surfaces to the local model.
2. Admit/prefill the sealed local model once and keep its weights, state and KV
   rows alive.
3. Let any local client append a scannerless `fcpa-task-frame` to the task spool,
   then write the FIFO bell. The bell carries no task data.
4. On CPU, admit only newly appended bytes, retain incomplete BMF cursor state,
   and make complete tasks present with an exact byte watermark.
5. Inject only the new task bytes into the resident model context.
6. When generated bytes complete a `form:recipe-exec` frame, resolve its NodeID,
   generate the native kernel, execute it, and inject the typed observation into
   the same KV stream.
7. Stage model response and cursor evidence as one length-carried output frame.
   Append it durably before promoting the returned session or marking the task
   seen.
8. On restart, rebuild replay knowledge from stable `exchange/turn` protocol
   keys. Intern-table instance coordinates are never treated as durable keys.
9. Keep recipe execution evidence distinct from research speech. A physical
   callback is contribution; direct speech remains a candidate until correlated
   evaluation observes `0` or `1`.

The live doors are:

- `observe/form-cli-peer-contribution-live.fk` — resident model, spool reader,
  contribution turnwheel, diagnostics and durable output.
- `observe/form-cli-peer-task-send.fk` — short-lived Form-native append/ring
  client; the task body may contain arbitrary newlines.

## Resource flow

| Work | Present carrier | Live observation |
|---|---|---|
| File delta, scannerless cursor, recovery, diagnostics | CPU / fkwu | wall time, kernel/framebuffer deltas, I/O dispatches |
| Local Qwen prefill and decode | native Metal | this process's `gpu_busy_us_total`, dispatch/sync/pending |
| Generated recipe kernels | native Metal today; NodeID route may evolve | cursor callback, carrier, value, native-code-generated, lifecycle |
| Adapter training or array work | MLX | this fkwu's `mlx_dispatch`; an external trainer enters as an explicit reservation observation |
| CPU JIT leaves | Form CPU JIT | `cpu_jit_busy_us_total` |

`metal_status` and `mlx_status` do not see another process's MLX queues or GPU
occupancy. A zero delta is therefore never interpreted as “the whole GPU is
idle.” The live runner accepts external MLX reservation as observed input, and
future host-utilization sensing can replace that supplied fact. Route and
quantum choice remain data; there is no fixed function-seat table.

## What remains northward

- Persist cursor evidence directly in every live output frame. The source now
  does this; the first physical run predates that widened frame and retained the
  evidence in resident state plus the next correlated response.
- Join client acknowledgement to compaction consent. Until durable client ack,
  reply frames remain append-only.
- Add capability-scoped source lookup and patch/application recipes so the
  agent can contribute repository changes, not only native recipe execution and
  evaluated research.
- Hot-swap the contribution recipe/turnwheel in a live residence. The current
  model/KV remains resident across tasks, but a source change still waits for a
  new process.
- Sense system-wide CPU/GPU/MLX pressure from a native host carrier rather than
  relying on process-local counters plus an explicit external reservation.
