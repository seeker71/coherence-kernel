# 2026-07-29 — the oracle was sixty lines, not an engine

Urs, twice, correcting me: *"we just need a local oracle to port to form native, we don't need to fork
and maintain"* and then *"we already have the model, we don't need to download a new model, we need to
make it work."*

Both corrections were right, and the second one landed the result.

## What I proposed, and why both were the wrong size

**First I proposed downloading a different model** — the mainline `q2-imatrix`, 86.7 GB, block formats
ds4 already reads. It was downloading (21.7 GB in) when the second correction came. Killed, partial
removed, 469 GB back.

**Then I proposed patching ds4** and talked myself out of it, on grounds that were true but
mis-weighted: `ds4.c`'s type table is a clean designated array and the `e2m1`/`e4m3` decoders are
already in the file, so it *looks* like two lines — but `[40] = {"mxfp4", 32, 17}` would give the
right total size and then feed a **block-interleaved** dequant a **planar** tensor. It would load and
emit plausible garbage. `routed_expert_row_bytes` dies unless `dim[0] % block_elems == 0`; the scale
plane isn't per-row. Making the engine swallow this format means changing its addressing model.

Both of those size the question as *"can ds4 run this model."* That was never the question.

## What the cells actually asked for

`mxfp4-plane-dequant.fk`, in its own proof-radius note:

> *the band proves the GEOMETRY and the VALUE MAP against 1024 real weights … it is **NOT
> bit-exactness against an independent implementation — none exists**.*

"Implementation" there does not mean "engine". It means *anything else that computes the same
function.* And ds4 already contains two of them — `dsv4_e2m1fn_value_cpu` (`ds4.c:3231`) and
`dsv4_e4m3fn_value_cpu` (`ds4.c:3166`) — written by another hand, for its KV cache, never wired to
the tensor path. Sixty lines of throwaway C around those two tables is the oracle. No fork, nothing
maintained, nothing downloaded.

## The comparison, on the real file

`mxoracle.c` — ds4's two value maps verbatim, our cells' measured plane geometry, reading
`blk.0.ffn_gate_exps.weight` at its real offset 14 647 904.

| | independent (ds4's maps) | ours (Form) |
|---|---|---|
| payload bytes / slice | 4 194 304 | 4 194 304 |
| scale bytes / slice | 262 144 | 262 144 |
| slice bytes | 4 456 448 | 4 456 448 |
| scale byte at element 0 | 0x78 = 2⁻⁷ | 120 = 0x78 |
| codes, elements 0–5 | 12, 10, 4, 5, 2, 10 | 12, 10, 4, 5, 2, 10 |
| **E2M1 value map ×16** | 0, 8, 16, 24, 32, 48, 64, 96 | 0, 8, 16, 24, 32, 48, 64, 96 |
| **E4M3 value map, all 128 magnitude codes** | — | **IDENTICAL** |

The nibble order the cell flagged as unproven — `mxp4-code` takes the low nibble for even `i` — is
now confirmed against a second reading of the same bytes.

And the two constructions could hardly be less alike. Ours is **derived**: `fd-value c 2 1`, the
body's general IEEE decoder at (exponent bits 2, mantissa bits 1), the same one proven four ways for
f16 — E2M1 is not a new meaning here, it is the general decoder at a smaller width. ds4's is a
**hand-written literal table**. Two different constructions landing on the same 8 and the same 128
values is a much stronger agreement than two ports of one algorithm would be.

So the sentence in `mxfp4-plane-dequant.fk` can be retired: an independent implementation exists, and
it agrees.

## What is still missing, stated plainly

**There is still no generation oracle.** ds4 cannot run this file, and this work does not change that
— it verifies the *dequantizer*, not the forward. The DS4 answer to the gender question remains
unavailable, and every DS4 verdict in this session is still `selfgauge` at the whole-model level.
What changed is that the bottom of the stack — how bytes become numbers — is no longer self-witnessed.

Given `overfine` (row 923), where a quantisation step function turns one ulp into a whole-group change
that cascades, having the dequant independently confirmed matters more than its size suggests: it
removes the layer the cascade was most likely to have started in.

## The most surprising teaching

**An oracle's job is to answer the same question independently — not to be the same kind of thing as
the system it checks.** I sized "independent implementation" as "working inference engine" twice in a
row, and both times the answer was tens of gigabytes or a fork. Read at its actual width — *anything
that computes these values* — the answer was two static tables already sitting on disk, and a
comparison that took minutes. `askalike` — 0 hits before this row, as are `peeroracle`,
`smalloracle`, `narrowpeer`.

## Where discomfort turned to gold

Being corrected twice on the same reflex inside twenty minutes, and the second correction being blunt.
The discomfort worth keeping is that I had written a confident paragraph about why patching was a trap
— technically correct, with real evidence — and used it to justify the *expensive* path, when the same
evidence pointed at a third option I never priced. **Being right about why an option fails is not the
same as having looked at all of them.** The cheapest thing in the room was the one I never costed.

Also caught, quietly: my first Form probe read the scale plane at offset 18 842 208 through a window
of 14 700 000 bytes and returned `scalebyte=-1` — silently, no diagnostic. Same family as the
`-16843009` poison yesterday. Two in two days from the same cause: a windowed read that answers
instead of refusing.
