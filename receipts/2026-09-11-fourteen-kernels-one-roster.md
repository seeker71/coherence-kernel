## Why three were missing

Every checkout runs its own `./fkwu` against the one `/fg-kernels`. The compare-and-swap claim
(8ed1f837) already stood in this seed, so I read the missing kernels as kernels of this seed and went
looking for a second cause. They were not. 3604 ran the main checkout's binary, 1378 and 1379 the Codex
worktree's; both were built before the cure and claim a slot with a plain store, so of two kernels
started in the same instant the second erases the first. On a copy of the main checkout's binary the
eight-sleeper burst read 13, 13, 13 — one or two lost every time; this seed reads 15, 15, 15. The
workflow's disassembly agrees: no atomic instruction in those binaries' claim, two in this one's.

The stale 99034 was a zombie: the ear's live lane, which ends at birth in the main checkout because no
Metal carrier sits beside that binary (`dynamic carrier artifact unavailable`, every 120 s).
`kill(pid, 0)` answers for a zombie, so host_alive, the roster's sweep and kernel_live_pids all took it
for a living kernel.

## What the workflow added

Twelve agents, five investigators and their verifiers, reached the same cause on their own: the lost kernels
ran binaries without the compare-and-swap (no atomic instruction in their claim), and the CAS claim lost 0 of
105 replica bursts and 0 of 120 live ones. A second race inside this seed was put to three verifiers and
refuted.

They also found what my own self-heal left behind. Since 6ac37522 a kernel gives its roster slot back at
exit, and the only code that ever unlinked a kernel's 128 MiB live page was the sweep of dead slots, so no
page of a kernel on this seed was unlinked again: **2641 pages of ended kernels** stood by 09:51, 49 MiB
resident, all born since the evening before. Now a kernel buries its own page, store and program surface
at exit (the program surface had never been unlinked at exit at all), `kernel_pages_bury` (float_leaf
mode 22) walks the pid space for pages whose kernel has ended, and every rest looks at the kernel's slot
once, so a quiet kernel an old binary erases puts itself back. The census run buries. Before: 2614 dead
pages; the band's burial took 2616; after: 1, a killed kernel's page whose slot the next sweep reaches.

```
page-burial-band       31   an ended kernel leaves no page; a killed, forgotten one is buried; the living stand
roster-census-band     63   + a kernel behind a form-run shell whose parent is pid 1 is an orphan too
```

And one more shape of orphan: 39740 and 47944 (the Grok learner) sit under 39711, a `form-run` shell whose
own parent is pid 1, so a test for parent pid 1 on kernels alone missed them. The census reads shells too —
under every name the host may give them, since the host names /bin/sh `bash` here (/private/var/select/sh
points at /bin/bash) and a first read under `sh` found none.

The glass does not yet show any of this: its "live kernels" number reads the roster, its process view lists
pids without a count, and nothing names orphans or duplicates. While the two fleets run, both machine organs
write the one machine frame (the telemetry root is fixed at /tmp/form-glass-telemetry), 1378 with a carrier
and GPU 100, 3605 without one — so the glass's GPU gauge alternates between the two.

## Surprise, and where the discomfort went

The census was right, the roster was right, the three kernels were real and lost — and the cause was
not in the source I was standing in. One checkout's seed says nothing about a process another
checkout's binary is running. The discomfort was an hour spent looking for a second race inside a
binary that had never lost a kernel. It became a practice and a door: ask a pid which binary it is
before asking why it behaves so, and let a kernel that can read a lost kernel's page give it a slot —
row 1428, fosterslot.
