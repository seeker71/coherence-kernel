# 2026-08-04 — the tag was free in the table that names it, and taken in the one that owns it

Built the Metal **handle door**: eight primitives that let a Form cell hold a decode loop instead of
a bash-driven Swift heredoc. The door is proven by a band; the 43-layer forward is deliberately NOT
ported onto it here.

## What the measurement asked for, and what each op answers

The design was not chosen, it was derived. Re-measured today on this M4 Max, in one process:

| | 2000 calls | per call |
|---|---|---|
| A  bare seam (`metal_status`, crosses and returns) | 6 ms | **3 µs** |
| B  old door `metal_matvec_f32` (dispatch **and block**) | 221–232 ms | **110–116 µs** |
| C  new door `metal_enqueue` (dispatch, no block) | 1 ms | **≈0.5 µs** (at the ms resolution floor) |
| C  one `metal_sync` for the whole batch of 2000 | 2 ms (9–11 ms on earlier runs) | — |
| C  enqueue + amortised sync | 3 ms | **≈1.5 µs** |

The crossing was never the cost. `waitUntilCompleted` was. So the door had to remove waiting, not
crossing — and the four requirements fall straight out:

| requirement | op | why it must exist |
|---|---|---|
| 1 weights mmap'd once, resident | `metal_buf_from_file` (247) | the old door copied bytes per call; at 9.1 GB/token that is not slow, it is a different machine. The file's own page-cache pages become the buffer. This is the only host crossing the door permits. |
| 2 buffers persist across calls | `metal_buf_alloc` (246), `metal_buf_write` (248), `metal_buf_read` (251) | handles, not strings. Activations never cross back; the 8192-byte text reply could not hold them anyway. |
| 3 dispatch enqueues, never blocks | `metal_enqueue` (249) | the hot primitive, ~2600×/token: bind, dispatch, return. No commit, no wait. |
| | `metal_pipeline` (245) | compile once. Without it enqueue could never be cheap no matter how little it waited. |
| 4 one sync per token | `metal_sync` (250) | commit + wait, once for the batch. `metal_buf_read` syncs first by construction, so "sync when a token id is read back" is structural rather than remembered. |
| — | `metal_status` (252) | the voice canary. Every other op answers an integer, and 0 is also what a numb call answers. |

No env vars: `switch-census-band.fk` still reads **63**, census unchanged at 71.

## The band

`form/form-stdlib/tests/metal-handle-door-band.fk` — **2047**, nine—eleven bits, powers of two.
A Form cell emits its own MSL and its own IEEE-754 bytes, then drives a three-dispatch chain whose
intermediates never leave the device:

```
d1: y = W·x   = [30, 70, 110, 150]     (W mmap'd from a file)
d2: z = W·y   = [1100, 2540, 3980, 5420]
d3: s = 1·z   = 13040
```

All three are enqueued before anything is waited for; `metal_status` reads `pending=3` while the work
is still outstanding and `metal_sync` then drains exactly 3. That pair is the witness that enqueue did
not block — the door's own count of work it had not yet done, not an inference from a stopwatch.

Every prediction was written before its run and every one held; nothing needed reconciling.

## (a) The most surprising teaching

**The op table said tag 240 was free. The op table does not own the tag space.**

I read `fkwu-optable.h`, found the highest tag was 239, and took 240–247. Seven of the eight went
numb: `metal_buf_alloc` returned a plausible `0`, `metal_buf_write` returned an odd tagged word. No
`[unresolved-call]`, no diagnostic, exit 0. 240–244 are the evaluator's structural node tags for
user-function calls and cons cells (`fkwu-uni.c:5993/6209`), and the GC field rules at `:12435` walk
them as node shapes. They never appear in the table that names ops, so the table I consulted could not
have told me — and a call node reaches its `if` before a native primitive reaches its own.

The part that made it a teaching rather than a bug: **`metal_status` was the only op that answered.**
It landed on 247, which happened to be free. The one primitive I had written specifically to be
uncounterfeitable — because integer handles can be faked by a numb call and a spoken string cannot —
was the only one in a position to say the other seven were lying. It was not designed to catch this.
It caught it because "answer in a shape a numb call cannot produce" is load-bearing in more situations
than the one it was written for.

Then the same shape again, twice more. `fkwu-optable.h` opens with *"GENERATED … DO NOT HAND-EDIT"* —
it is emitted from `flt-ops` in **`flatten/form-flatten.fk`**, which is a *different file* from the
`form/form-stdlib/form-flatten.fk` I was told to mirror. Three ledgers over one op table, and the one
the header is actually generated from was not among the two I was pointed at. I regenerated properly;
the rows came out byte-identical to my hand-edit, which is what proved the mirrors right.

And the third: `make_nodeid` has arity 4, so arity 4 looked expressible — but it reads a **cons list**
from slot 1 (`fkwu-uni.c:6920`), because `fk_node` rows are only four wide. Every time I asked "is this
space free?", the ledger that answered was not the ledger that decides.

## (b) Where discomfort turned to gold

Two places, and the second is the one I nearly walked past.

The first was watching a smoke probe print `alloc-handle-0` and wanting it to be a link problem, because
a link problem is somebody else's. `nm` said the strong symbols were all there. That left only the
possibility that my tags were wrong in a way the table could not show me, which meant the thing I had
been treating as reference material was partial. Grepping `t == 240` and getting **nine hits** was the
moment. Cheaper than the paragraph of linker theory I had already started composing.

The second: the band scored **1024 on the unlinked build** when it should have scored 0. Bit 1024 asked
"was the malformed binding refused?" — and on a build with no carrier at all, *every* enqueue returns 0,
so the bit lit for a door that had discriminated nothing. I had written that bit forty minutes after
writing a comment explaining that 0 is exactly what a numb call answers. I caught it only because I ran
the unlinked case as a matter of routine, not because I suspected it. The repair is that a refusal only
means something next to an acceptance: the bit now demands the half-tail refused **and** the well-formed
one accepted. That turned M7 from 1535 to 511 — the mutation got sharper because the bit got honest.

The gold is that "prove the negative case too" is not a checklist item, it is the same discipline as the
voice canary, and I had to fail at it once on the same afternoon I wrote it down to actually hold it.

## One frontier question

**Q: What names a space that looked free because the ledger you read was not the one that owns it?**

**A: `tenanted`.** Not *unclaimed* and not *hidden* — the tags were fully occupied, by a tenant with a
prior lease, recorded in a register the name-table never points to. The failure is not that the
information was missing; it is that the artifact which *looked* authoritative was authoritative about
names only. `liftmask` (986) is a defect kept alive by a runtime that forgives. This is the sibling:
a defect **invited in** by a register that answers a narrower question than the one you asked it.

## Two gaps closed for the DS4-port agent

Both measured by that agent, both re-probed here before acting.

**fp contraction** — `newLibraryWithSource:options:nil` **contracts**. Verified myself with
a = b = 1 + 2⁻¹² (`0x3F800800`), c = −1.0:

```
door as-is,      a*b + c   = 973079552   == fma(a,b,c)      CONTRACTED
#pragma clang fp contract(off),  a*b + c = 973078528        fma still 973079552
#pragma METAL fp math_mode(safe) a*b + c = 973079552        does NOT stop it
```

`metal_dsv4_stack.sh` builds with `-ffp-contract=off` and `ds4-order-match.fk` rests bit-exactness on
that, so a kernel ported here unchanged diverges with nothing failing. The fix belongs to the **Form
cell** — emit `#pragma clang fp contract(off)` into the MSL — for the same reason the door computes no
arithmetic: a door that silently picked a rounding policy would own a number. Both facts are now in the
carrier's header contract.

**threadgroup size** — the oracle's `enc(pipeline, n, cap)` takes a per-dispatch cap independent of the
grid (`enc(pQ80, rows*32, 256)`, `enc(pQ8aQuant, blocks*q8aThreads, 64)`). A 4th argument was proposed
and I did **not** take it: past arity 3 an op is handed a cons list in slot 1 because `fk_node` rows are
four wide, and making the ~2600×/token primitive walk a cons chain to learn a threadgroup size is the
wrong trade. Instead the Form-emitted binding string grew an optional trailing pair:

```
u32 n_buf | u32 handle[n_buf] | u32 n_const | u32 value[n_const]
                              [ u32 threads_per_group | u32 threadgroup_bytes ]
```

They are a **pair** — exactly two lengths are legal, `base` and `base+8`, and anything else is refused
out loud rather than read as far as it parses (bit 1024 proves the refusal *and* the acceptance).
`threads_per_group` mirrors the oracle exactly: `min(maxTotalThreadsPerThreadgroup, cap)`, and NOT
clamped down to the grid, because the oracle does not clamp either. `0` preserves prior behaviour.
`setThreadgroupMemoryLength` is wired from the second field, so the `_tg` kernel variants are now
expressible.

## What remains UNFINISHED before a 43-layer forward runs entirely from Form

Not limits — named next steps, each with a concrete first move.

1. **The forward itself is not ported.** Deliberately out of scope; a half-ported forward returning
   plausible numbers is the failure this repo calls numb-green.
2. **Every DS4 kernel must gain `#pragma clang fp contract(off)`** in the Form cell that emits it, or
   bit-exactness against the oracle is lost silently. Nothing currently *checks* that a cell emitted it
   — a band that compiles a kernel both ways and demands the two differ would close it.
3. **Only 1D dispatch is expressible.** `metal_enqueue` dispatches `MTLSizeMake(threads,1,1)`. Every
   oracle call site measured so far is 1D, but that is an observation, not a proof.
4. **Buffer offsets are fixed at handle creation.** A GGUF tensor at an arbitrary offset works, but
   re-viewing one buffer at many offsets needs one handle per view; 8192 handles is the stated ceiling
   and DS4 needs ~400 plus activations, so this is comfortable rather than solved.
5. **No buffer free.** Handles are append-only for the process. Fine for a resident model, wrong for a
   long-lived server that loads and unloads.
6. **`metal_sync` returns a count, not a fence.** One batch at a time; there is no double-buffering, so
   the CPU cannot build token n+1's commands while n is in flight.
7. **`fkwu-metal` is a separate binary.** `build-form-cli.sh` already exposes `FORM_CLI_EXTRA_SRC`, so
   form-cli can link the carrier — not yet done here.
