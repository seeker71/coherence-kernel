# 2026-08-04 — the freed slot re-let, and the third register that owned what a table listed

Second growth of the Metal handle door, same day, asked for by the first fully-form-native decode
through it (llama3.2:3b, 12/12 ids against the oracle). Four asks from that port, four answers, all
proven from Form cells through the door only — no Swift comparator anywhere, per the standing word
"no swift no external tools".

## What was built

**1. Cooperative dispatch (`dispatchThreadgroups`).** No new op. The binding string grew a THIRD legal
length — base+16 adds `dispatch_mode` and `barrier_before` — still refused out loud at any other
length (the half-tail mutation M6 still refutes). With mode 1 the op's `threads` argument is the GROUP
count, `threads_per_group` is exact and REFUSED past the pipeline's ceiling rather than clamped,
because silently shrinking T repartitions the very fold the mode exists for.

**2. Concurrent encoder with declared hazards.** `metal_batch_concurrent` (253) arms the NEXT batch;
the encoder opens `MTLDispatchTypeConcurrent`; `barrier_before` in the binding emits
`memoryBarrier(scope: buffers)` before that dispatch. The CELL declares every hazard — the door
guesses nothing, because a door that guessed hazards would own correctness and this one owns none.
`barrier_before` in a SERIAL batch is turned away: a cell that asks for a barrier believes it is in a
concurrent batch, and that belief misplaces hazards. Judged BEFORE the batch opens, so a refused
enqueue leaves no half-open state.

**3. `metal_buf_free` (254), with generations.** A handle is now `(gen << 16) | slot`. Freeing bumps
the slot's generation and pushes it on a free list; a fresh alloc re-lets the slot under the new
generation. Every outstanding handle to the old tenant stops matching and is refused at the door —
witnessed by the band's sharpest probe, a stale read AFTER the slot is reused, where a
generation-less door would answer with the new tenant's bytes. Generation 0 keeps every pre-free
handle value numerically unchanged, so nothing that held a handle before this scheme sees a different
number. Free demands a quiescent door (nothing open, nothing in flight): Metal would keep a plain
buffer alive through a referencing command buffer, but an mmap'd one is OUR mapping under Metal's
object, and munmap under a running dispatch is a fault Metal cannot see coming. One rule for both,
stated. The 16-bit generation wraps at 65536 reuses of one slot; said here rather than discovered.

**4. `metal_submit` (255) / `metal_fence_wait` (142).** Submit commits WITHOUT waiting and answers a
fence id; fence_wait drains that one batch and answers its dispatch count — proof the work was
outstanding. A second wait on a spent fence answers 0 with the refusal spoken, because a wait that
"succeeds" on a fence nobody holds is how a double-buffered loop drifts one token out of step
silently. An empty batch earns no fence — a fence id for nothing is a number wearing a meaning.
`metal_sync` and `metal_buf_read` drain in-flight batches too, so "read is the sync point" survives
fences. Double-buffering is now expressible: enqueue token n, submit, build token n+1 while n runs,
fence_wait(n).

## One frontier question

**Q: What names the discipline of probing a freed thing again AFTER its place is re-let, when the
probe before re-letting cannot tell a generation from a coincidence?**

**A: `retenant`.** The band's stale read immediately after free proves little — the slot was empty,
any door answers empty. The probe that discriminates is after a NEW tenant moves in: a door without
generations answers the old key with the new tenant's bytes, and only the generation stamp refuses.
The witness must wait for the re-letting, because before it the honest door and the dangerous door
answer alike.
